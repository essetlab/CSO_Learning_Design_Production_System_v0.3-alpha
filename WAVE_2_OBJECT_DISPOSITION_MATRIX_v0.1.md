## Consolidation decisions

No whole object is recommended for deprecation or forced merger at this stage. Genuine repeated responsibilities are **inside** objects: recovery/consent/receipt presentation, export action controls, neutral workspace layout scaffolding and primitive DOM/text/rubric helpers. Extract them through explicit shared interfaces when the next consumer establishes the need. Keep artifact semantics, repair/evidence-update state machines and scene interpretation separate.

The strongest missing shared primitive is a rendering interface for the existing service's recovery/receipt/consent choices. It must expose versions and failures truthfully and delegate all service calls and learning decisions appropriately. The present UI-SAVE-STATE-01 CSS does not itself supply that behavior. This is a proposal for governed scope, not a new silently named/registered object.

Shared services are cross-cutting architecture, not another visual layer in Token → UI Primitive → Component → Learning Block → Interaction → Practice/Ecosystem Object → Composition → Template → Screen Instance → Instructional Pattern. The registry's mixed container is acceptable if each entry's type, implementation maturity, dependency interface, scope and status are explicit. Neither manifest-only patterns nor executable objects should masquerade as the same validation maturity.
